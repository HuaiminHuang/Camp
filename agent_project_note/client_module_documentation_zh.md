# 客户端模块文档

## 概述

`client` 模块是车载助手代理面向用户的组件。它负责处理用户输入、协调各种后端服务并生成响应。该模块由几个子模块组成，每个子模块在对话管道中都有特定的角色。

## 核心组件

`client` 模块包含以下 Python 脚本：

- `nlu.py`: 自然语言理解
- `nlg.py`: 自然语言生成
- `arbitration.py`: 对话仲裁
- `correlation.py`: 查询相关性
- `rewrite.py`: 查询重写
- `reject.py`: 拒绝处理
- `stream_chat.py`: 流式聊天

### `nlu.py` - 自然语言理解

**目的:** 此模块负责解释用户的意图并从其查询中提取相关信息（槽位）。

**功能:**
- `request_nlu` 函数将用户的查询发送到专用的 NLU 服务（由 `NLU_URL` 环境变量定义）。
- NLU 服务处理查询并返回一个 JSON 对象，其中包含已识别的意图和任何关联的槽位（例如，对于天气查询，意图可能是 `get_weather`，槽位可能包括 `city` 和 `date`）。

### `nlg.py` - 自然语言生成

**目的:** 此模块根据代理工具的输出生成人类可读的响应。

**功能:**
- `request_nlg` 函数将原始用户查询和 `tool_response`（从工具调用返回的数据）作为输入。
- 它使用强大的语言模型（豆包）来制作一个听起来自然的句子，向用户呈现工具的输出。例如，如果工具返回 `{"temperature": "25°C", "condition": "Sunny"}`，NLG 模块可能会生成响应：“当前温度为 25 摄氏度，天气晴朗。”

### `arbitration.py` - 对话仲裁

**目的:** 此模块充当代理的中央路由器，决定应由哪种能力（面向任务、FAQ 或聊天）处理用户的查询。

**功能:**
- `request_arbitration` 函数使用语言模型（豆包）将用户的查询分为以下几类：
    - **“A”（任务）:** 用户想要执行特定操作（例如，“导航回家”、“播放音乐”）。
    - **“B”（FAQ）:** 用户正在问一个可以从知识库中回答的问题。
    - **“C”或“D”（聊天）:** 用户想要进行一般性对话。
- 它在 Redis 中维护一个简短的对话历史，为分类提供上下文。

### `correlation.py` - 查询相关性

**目的:** 此模块确定新的用户查询是否与对话的上一轮相关。这对于处理更正和后续问题至关重要。

**功能:**
- `request_correlation` 函数将当前查询与存储在 Redis 中的上一个查询及其结果进行比较。
- 它使用语言模型（豆包）来确定新查询是否是上一个查询的延续或修改（例如，用户：“显示我附近的餐馆”，代理：“我找到了 5 家餐馆...”，用户：“意大利菜怎么样？”）。
- 如果查询相关，则返回“是”，否则返回“否”。

### `rewrite.py` - 查询重写

**目的:** 此模块提高了用户查询的清晰度和完整性，尤其是在多轮对话中。

**功能:**
- `request_rewrite` 函数使用对话历史（来自 Redis）和语言模型（豆包）来扩展和消除用户查询的歧义。
- 例如，如果用户说“明天怎么样？”，此模块可以根据先前的上下文将其重写为更完整的查询，如“明天的天气怎么样？”。

### `reject.py` - 拒绝处理

**目的:** 此模块用作安全过滤器，以识别和拒绝不当或超出范围的用户查询。

**功能:**
- `request_reject` 函数将用户的查询发送到拒绝服务（由 `REJECT_URL` 定义）。
- 此服务使用模型对查询进行分类，并确定是否应由代理处理。
- 它返回“是”（即查询被接受）或“否”（即查询被拒绝）。

### `stream_chat.py` - 流式聊天

**目的:** 此模块使代理能够与用户进行开放式的对话聊天，并将响应逐字流式传输回用户。

**功能:**
- `request_chat` 函数将用户的查询发送到特定于聊天的语言模型（豆包）。
- `process_chat` 函数以流的形式从模型接收响应，并将其分块地提供给用户，从而创建实时聊天体验。
- 它还在 Redis 中维护聊天记录，以支持多轮对话。

## 数据流

用户查询通过 `client` 模块的典型流程如下：

1.  接收用户的原始查询。
2.  `reject` 模块可以首先出于安全考虑过滤查询。
3.  `arbitration` 模块确定总体意图（任务、FAQ 或聊天）。
4.  **如果意图是“任务”：**
    a. `correlation` 模块检查查询是否与上一轮相关。
    b. `rewrite` 模块可以澄清和扩展查询。
    c. `nlu` 模块提取特定的意图和槽位。
    d. NLU 输出用于调用适当的工具/功能。
    e. 工具的输出将传递到 `nlg` 模块以生成最终响应。
5.  **如果意图是“聊天”：**
    a. 查询将发送到 `stream_chat` 模块，该模块处理会话响应。

这种模块化体系结构可以清晰地分离关注点，并使代理更易于开发、调试和维护。
